# T02.2: Logging and telemetry with Azure Application Insights

**User story:** [US-001](../US-001-SuperHero-Registry.md) · **Layer:** Cross-cutting (ServiceDefaults, Api, Infrastructure) · **Estimate:** 4 h · **Depends on:** T02 · **Status:** Done (repositories in T05 and T06 call the data-layer timer built here)

## Goal
Send the API's logs and telemetry to **Azure Application Insights**, so the team can see:
1. **Every request to an endpoint**: route, HTTP verb, status code, duration, failures and exceptions.
2. **Every database interaction**: the `SELECT`, `INSERT`, `UPDATE` and soft-`DELETE` statements run by the data layer, with timing (a data-layer timer), the affected table and row counts, and errors.

The Aspire dashboard keeps working in development. The same telemetry goes to both destinations. **Nothing changes on SQL Server.**

## Approach
ServiceDefaults already builds an **OpenTelemetry** pipeline (T02). Application Insights is added as a second **exporter** (`Azure.Monitor.OpenTelemetry.Exporter`) on that same pipeline.

The full Azure Monitor *distro* (`Azure.Monitor.OpenTelemetry.AspNetCore`) was evaluated and **not used**, for two reasons:
- It bundles a private copy of the SqlClient instrumentation that is active only when Application Insights is on. SQL spans would then be missing from the Aspire dashboard whenever Application Insights is off.
- Adding the standalone SqlClient instrumentation next to it would duplicate every SQL span, and the two packages' `AddSqlClientInstrumentation` extension methods would clash.

With the exporter, we own the instrumentation: request and SQL spans are identical in the Aspire dashboard and Application Insights.

| What                    | Source                                                        | Application Insights table |
| ----------------------- | ------------------------------------------------------------- | -------------------------- |
| Requests to endpoints   | ASP.NET Core instrumentation (ServiceDefaults)                | `requests`                 |
| SQL commands            | `OpenTelemetry.Instrumentation.SqlClient` (client-side)       | `dependencies`             |
| Data-layer operations   | `DataAccessInstrumentation` (`HeroRegistry.Data` spans)       | `dependencies`             |
| Structured logs         | `ILogger` with source-generated `DataAccessLog`               | `traces`                   |
| Unhandled exceptions    | ASP.NET Core instrumentation (`RecordException`)              | `exceptions`               |

## Steps

### 1. Configuration cleanup
- [x] Removed `Logging:ApplicationInsights` and `APPLICATIONINSIGHTS_CONNECTION_STRING` from the **AppHost** `appsettings.json`. The AppHost only orchestrates; the **API** sends telemetry. The API's user secrets already contain the connection string, and they are loaded under Aspire too.
- [x] Removed the `"<use secrets>"` placeholder. It is now **rejected at startup** with a clear message.
- [x] Dropped the `Microsoft.EntityFrameworkCore.*` categories (Entity Framework is not used).
- [x] Dropped `enableDependencyTracking` and `dependencyTrackingOptions`. These are Azure Functions `host.json` settings and are ignored by ASP.NET Core.
- [x] API `appsettings.json` has `Logging:OpenTelemetry:LogLevel`. The OpenTelemetry provider alias is `OpenTelemetry`, not `ApplicationInsights`. Data-layer logs are at `Information`, and at `Debug` in `appsettings.Development.json` so reads show up locally.
- [x] Docker Compose: documented in [T15](T15-Docker-Compose.md) (`APPLICATIONINSIGHTS_CONNECTION_STRING` from `.env`, `OTEL_SERVICE_NAME`).

### 2. Exporter (ServiceDefaults)
- [x] `Azure.Monitor.OpenTelemetry.Exporter` 1.10.0 is used with `UseAzureMonitorExporter()`, **only when** `APPLICATIONINSIGHTS_CONNECTION_STRING` is set (`AzureMonitorSettings.TryGetConnectionString`).
- [x] The existing OTLP exporter for the Aspire dashboard stays. Both exporters can be active.
- [x] Service name (cloud role name):
  - `OTEL_SERVICE_NAME` when set. Aspire sets it to `api`, and its dashboard relies on it.
  - Otherwise the application name (`HeroRegistry.Api`).
- [x] Sampling: `ApplicationInsights:SamplingRatio` (default 1.0, validated to be between 0 and 1). `TracesPerSecond` is cleared, because it would override the ratio.
- [x] `HeroRegistry.*` ActivitySources and Meters are collected.

### 3. Requests to endpoints
- [x] ASP.NET Core instrumentation with `RecordException = true`. `/health` and `/alive` are filtered out.
- [ ] Enrich request telemetry with the user id (`enduser.id`) once authentication exists. **Moved to T09.**

### 4. Database interactions (SELECT, INSERT, UPDATE, soft DELETE)
- [x] `AddHeroRegistrySqlClientInstrumentation()` (ServiceDefaults) traces every SQL command client-side, with the command text and duration.
  - Parameter values are not captured (the instrumentation's default).
  - Literals in SQL text are replaced by `?`.
  - Exceptions are not attached (`RecordException = false`), because SQL Server's messages can echo data.
  - Trace context propagation (`SET CONTEXT_INFO`) stays off, so nothing extra runs on SQL Server.
- [x] **Data-layer timer**: `DataAccessInstrumentation` (Infrastructure, singleton) with `Begin(DataOperation, table, id)`, which returns a `DataOperationScope`. The scope takes `Succeeded(rowCount, id)` or `Failed(exception)`. It provides:
  - A `TimeProvider`-based timer, so tests control time.
  - One span per operation (`INSERT SuperHeroes`, `SOFT DELETE SuperHeroes`, ...) with tags `db.system.name`, `db.operation.name`, `db.collection.name`, `heroregistry.entity.id`, and `heroregistry.rows_affected` or `db.response.returned_rows`.
  - `DataAccessLog` (source-generated):
    - Information: Inserted, Updated, Soft-deleted.
    - Debug: Selected.
    - Warning: slow operations over `Database:SlowCommandThresholdMs` (default 500, 0 disables).
    - Error: failures, with the exception type and SQL error number but **not the message**.
- [x] Health-check queries run inside `SuppressInstrumentationScope`, so Aspire's `/health` polling doesn't flood Application Insights.
- [ ] Call `DataAccessInstrumentation` from `SqlRepository<T>` and the repositories. **Done in T05 and T06** (noted in T05).

## Tests (TDD)
All tests were written before the implementation. Each guard was also checked "red": with the safeguard temporarily removed, its test failed.

- **ServiceDefaults.Tests** (new project, 20 tests):
  - Connection string missing, empty or whitespace means disabled; a valid one enables Application Insights; a placeholder throws without echoing the value.
  - Sampling ratio defaults and validation.
  - The exporter is registered only when configured, and uses the configured connection string and sampling ratio.
  - Service name rules: the default, and Aspire's `OTEL_SERVICE_NAME` is kept.
- **Infrastructure.Tests:**
  - `DataAccessInstrumentationTests` (FakeLogger, FakeTimeProvider, ActivityListener): the message, level and properties for each operation; slow warning thresholds; failure logs without the exception message; span names and tags; error status; single completion; guard clauses.
  - `SqlClientTelemetryTests` (real SQL Server, Testcontainers):
    - Commands are traced with their text but **no parameter values**.
    - A real duplicate-key error (whose message contains the email) leaks **nothing** into the span.
    - Literals are scrubbed.
    - Health-check queries are not traced.
  - DI: the instrumentation is registered, and the slow threshold is bound and validated.
- **Api.Tests:**
  - Requests are exported with their method and status code, and `/health` and `/alive` are not.
  - `TelemetryIsolationTests`: **tests never export to Application Insights**, even though Development loads the developer's user secrets with a real connection string. All API tests now use `HeroRegistryApiFactory`.

## Implementation notes
- **Packages:**
  - `Azure.Monitor.OpenTelemetry.Exporter` 1.10.0.
  - `OpenTelemetry.Instrumentation.SqlClient` 1.20.1.
  - `OpenTelemetry` 1.20.1 in Infrastructure, for `SuppressInstrumentationScope`.
  - Tests: `OpenTelemetry.Exporter.InMemory`, `Microsoft.Extensions.Diagnostics.Testing` (`FakeLogger`) and `Microsoft.Extensions.TimeProvider.Testing`.
- **SqlClient options:** `SetDbQueryParameters` and `EnableTraceContextPropagation` are not public in 1.20.1. They can only be switched on by experimental `OTEL_DOTNET_EXPERIMENTAL_SQLCLIENT_*` environment variables, which this project never sets. Their safe defaults are relied on, and the tests prove them.
- **Test isolation:** `HeroRegistryApiFactory` sets the connection string to whitespace (meaning disabled) with `UseSetting`. The isolation test failed without it, which confirms that user secrets are loaded during tests.
- **PII rule for later tasks:** T06 must translate `SqlException` 2601 and 2627 (unique violations) into `DuplicateEntityException` with no values. The raw message contains the duplicate value and would otherwise reach request exceptions. T11's exception handler must not log raw `SqlException` messages either.

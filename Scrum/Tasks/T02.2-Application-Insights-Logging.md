# T02.2: Logging and telemetry with Azure Application Insights

**User story:** [US-001](../US-001-SuperHero-Registry.md) · **Layer:** Cross-cutting (ServiceDefaults, Api, Infrastructure) · **Estimate:** 4 h · **Depends on:** T02 (the database part is completed with T05 and T06)

## Goal
Send the API's logs and telemetry to **Azure Application Insights**, so the team can see:
1. **Every request to an endpoint**: route, HTTP verb, status code, duration, failures and exceptions.
2. **Every database interaction**: the `SELECT`, `INSERT`, `UPDATE` and soft-`DELETE` statements run by the Reflection data layer, with timing, the affected table and row counts, and errors.

The Aspire dashboard keeps working in development. The same telemetry goes to both destinations.

## Approach
ServiceDefaults already builds an **OpenTelemetry** pipeline (T02). Add the **Azure Monitor OpenTelemetry distro** (`Azure.Monitor.OpenTelemetry.AspNetCore`) to that same pipeline, instead of the classic `Microsoft.ApplicationInsights.AspNetCore` SDK. With one pipeline and two exporters (OTLP to the Aspire dashboard, Azure Monitor to Application Insights), request, dependency and log data is identical in both places.

| What                    | Source                                                        | Application Insights table |
| ----------------------- | ------------------------------------------------------------- | -------------------------- |
| Requests to endpoints   | ASP.NET Core instrumentation (already in ServiceDefaults)     | `requests`                 |
| SQL commands            | `OpenTelemetry.Instrumentation.SqlClient` (Microsoft.Data.SqlClient) | `dependencies`      |
| Data-layer operations   | `ActivitySource("HeroRegistry.Data")` spans in `SqlRepository<T>` | `dependencies`         |
| Structured logs         | `ILogger` (source-generated `LoggerMessage`)                  | `traces`                   |
| Unhandled exceptions    | ASP.NET Core instrumentation and the exception handler (T11)  | `exceptions`               |

## Steps

### 1. Configuration cleanup (the current setup needs fixing)
The values added to `HeroRegistry.AppHost/appsettings.json` don't take effect where they are:
- [ ] Remove the `Logging:ApplicationInsights` section and `APPLICATIONINSIGHTS_CONNECTION_STRING` from the **AppHost** `appsettings.json`. The AppHost only orchestrates; the **API** is what sends telemetry. The API's user secrets already contain `APPLICATIONINSIGHTS_CONNECTION_STRING`, and they are loaded under Aspire too, because Aspire runs the API in the Development environment.
- [ ] Remove the `"<use secrets>"` placeholder. A non-empty value turns the exporter on, and an invalid connection string fails at startup. A **missing** key is the correct way to say "not configured".
- [ ] Drop the `Microsoft.EntityFrameworkCore.*` categories. Entity Framework is not used in this project.
- [ ] Drop `enableDependencyTracking` and `dependencyTrackingOptions`. These are **Azure Functions `host.json`** settings and are ignored by ASP.NET Core. Their purpose (SQL command text) is covered by step 3.
- [ ] Put the log filtering in the **API**'s `appsettings.json`. With the OpenTelemetry distro, the logging provider alias is **`OpenTelemetry`**, not `ApplicationInsights`:
  ```json
  "Logging": {
    "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" },
    "OpenTelemetry": {
      "LogLevel": {
        "Default": "Information",
        "Microsoft": "Warning",
        "HeroRegistry.Infrastructure.Persistence": "Information"
      }
    }
  }
  ```
- [ ] Docker Compose (T15): pass `APPLICATIONINSIGHTS_CONNECTION_STRING` from `.env` (add it to `.env.example` with an empty value).

### 2. Exporter (ServiceDefaults)
- [ ] Add `Azure.Monitor.OpenTelemetry.AspNetCore` to `HeroRegistry.ServiceDefaults`.
- [ ] In `AddOpenTelemetryExporters()`, call `builder.Services.AddOpenTelemetry().UseAzureMonitor()` **only when** `APPLICATIONINSIGHTS_CONNECTION_STRING` is set. Without it, the API runs normally (tests, CI, a fresh clone).
- [ ] Keep the existing OTLP exporter for the Aspire dashboard. Both exporters can be active.
- [ ] Set the cloud role name to `hero-registry-api` (`OTEL_SERVICE_NAME` or a resource builder), so the Application Map shows a meaningful node.
- [ ] Sampling: 100% in Development. Make it configurable (`ApplicationInsights:SamplingRatio`) for other environments.

### 3. Requests to endpoints
- [ ] Keep the ASP.NET Core instrumentation. `/health` and `/alive` stay filtered out, so probes don't flood Application Insights.
- [ ] Record exceptions on request spans (`RecordException = true`).
- [ ] Once authentication exists (T09), enrich the request telemetry with the user id (`enduser.id`), never the user name or email.
- [ ] Add a structured log scope per request (route and trace id) so `traces` and `requests` correlate (`operation_Id`).

### 4. Database interactions (SELECT, INSERT, UPDATE, soft DELETE)
- [ ] Add `OpenTelemetry.Instrumentation.SqlClient` to the tracer (`AddSqlClientInstrumentation`). Every command becomes a dependency with the server, database, duration and success flag.
  - Record the **command text**. All SQL is parameterized (T05), so the text contains `@HeroName`-style placeholders, never values.
  - **Never** record parameter values. They contain personal data: names, emails, addresses and password hashes.
- [ ] Add `ActivitySource("HeroRegistry.Data")` in Infrastructure and register it in the tracer (`AddSource`). `SqlRepository<T>` (T05) starts one span per operation:
  - Span name: `{Operation} {Table}`, for example `INSERT SuperHeroes`.
  - Tags: `db.operation.name` (SELECT, INSERT, UPDATE or DELETE), `db.collection.name` (table), `heroregistry.entity.id` (key, when known) and `heroregistry.rows_affected`.
  - On failure: status Error, with the exception recorded.
- [ ] Add a source-generated **`DataAccessLog`** (`[LoggerMessage]`, category `HeroRegistry.Infrastructure.Persistence`). `SqlRepository<T>` (T05) and the repositories (T06) call it:
  - `Information`: "Inserted {Table} row {Id} in {ElapsedMs} ms", "Updated {Table} row {Id} ({RowsAffected} rows) in {ElapsedMs} ms", "Soft-deleted {Table} row {Id} in {ElapsedMs} ms".
  - `Debug`: "Selected {RowCount} {Table} rows in {ElapsedMs} ms" (reads are frequent, so they log at Debug to control cost).
  - `Warning`: slow commands over a configurable threshold (`Database:SlowCommandThresholdMs`, default 500 ms).
  - `Error`: failed commands, with the `SqlException` number and the table. **No parameter values.**
- [ ] Until T05 and T06 exist, deliver the `ActivitySource`, `DataAccessLog` and their registration with tests. T05 and T06 then call them from the repository code.

### 5. Documentation
- [ ] README: how to enable Application Insights (user secret for development, `.env` for Compose), and useful KQL queries:
  ```kusto
  requests | where cloud_RoleName == "hero-registry-api" | summarize count(), avg(duration) by name, resultCode
  dependencies | where type == "SQL" | project timestamp, name, data, duration, success
  traces | where customDimensions.CategoryName startswith "HeroRegistry.Infrastructure.Persistence"
  ```

## Tests (TDD)
- [ ] ServiceDefaults: the Azure Monitor exporter is registered when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set, and is **not** registered when it is missing or empty. The API still starts in both cases.
- [ ] `DataAccessLog`: use `FakeLogger` (`Microsoft.Extensions.Diagnostics.Testing`) to verify the level, the message and the structured properties (Table, Id, ElapsedMs, RowsAffected) for each operation. Verify that no parameter value (for example a test email) ever appears in a log record.
- [ ] `HeroRegistry.Data` spans: an `ActivityListener` captures one span per repository operation with the expected name, tags and an error status on failure. These are integration tests with Testcontainers, together with T05 and T06.
- [ ] Api: a request to `/api/v1/test` produces a request activity, and `/health` does not (filter).

## Security and privacy
- The connection string lives only in user secrets (development) or environment variables (`.env`, Compose). It is never committed.
- No personal data in telemetry: no parameter values, emails, names, addresses or password hashes. Only ids, tables, timings and counts.
- SQL command text is safe to send because every statement is parameterized (enforced in T05).

## Done when
- With the connection string set, Application Insights shows:
  - `requests` for API calls (not health probes).
  - `dependencies` of type SQL with the command text.
  - `traces` from `HeroRegistry.Infrastructure.Persistence` for inserts, selects, updates and soft deletes.
  - All correlated by `operation_Id` in the transaction view.
- Without the connection string, the API, the tests and CI run unchanged.
- The Aspire dashboard still shows the same traces, logs and metrics.
- The build has 0 warnings, and all tests pass.

# T09.1: Refresh tokens (HttpOnly cookie, rotation and logout)

**User story:** [US-001](../US-001-SuperHero-Registry.md) (AC2, **AC12**) · **Layer:** Domain, Application, Infrastructure and API · **Estimate:** 5 h · **Depends on:** T06, T08, T09 · **Status:** Done

## Goal
Let the Angular app keep the access token **in memory only** (never in `localStorage` or `sessionStorage`) and still keep the user signed in across page reloads and token expiry. The access token is short-lived. A long-lived, **rotated refresh token** lives in an **HttpOnly cookie** that JavaScript cannot read, so an XSS attack cannot steal it.

## Design
| Token | Lifetime | Where it lives | Sent as |
| ----- | -------- | -------------- | ------- |
| Access token (JWT) | **15 min** (`Jwt:ExpirationMinutes`, down from 60) | Angular memory (a signal) | `Authorization: Bearer` header |
| Refresh token (opaque, 256-bit random, not a JWT) | **7 days** (`RefreshToken:LifetimeDays`) | HttpOnly cookie, and only its **SHA-256 hash** in the database | Cookie, sent by the browser only to `/api/auth` |

- **Cookie:** `hr_refresh`, with `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/auth` and `Expires` set to the token's expiry. Browsers accept `Secure` cookies on `http://localhost`.
- **Same origin, no CORS credentials:** the UI always calls the API through a proxy: the Angular dev proxy under Aspire (T02), and nginx in Docker Compose (T15). The browser therefore sends the cookie without `withCredentials` or `AllowCredentials()`. `SameSite=Strict` plus POST-only endpoints protect against CSRF.
- **Rotation:** every refresh revokes the presented token and issues a new one in the same **family** (one family per login).
- **Reuse detection:** if an already-rotated token is presented again (outside the grace window), it was probably stolen, so **the whole family is revoked** and the user must sign in again.
- **Grace window** (`RefreshToken:ReuseGraceSeconds`, 30 s): two tabs reloading at the same moment can both send the old cookie. If a token was rotated less than 30 s ago, the API returns `401` with code `auth.refresh_race` **without** revoking the family. The UI then retries once, because the browser now holds the new cookie.
- **Why SHA-256 and not BCrypt for the hash:** the token is 256 bits of randomness, so a fast hash is safe and lets the API look it up by an indexed column.

## Steps
- [x] **Domain:** `RefreshToken` entity with `Id`, `UserId`, `TokenHash`, `FamilyId`, `CreatedAt`, `ExpiresAt`, `RevokedAt` and `ReplacedByHash`. Add `IsActive(now)`, `Revoke(now, replacedBy?)` and `WasRotatedWithin(now, window)`. Constructors are guarded (T04 style).
- [x] **Migration** `0004_CreateRefreshTokens.sql`:
  - Columns as above. `FK UserId -> Users(Id)`.
  - Unique index on `TokenHash`, plus an index on `(UserId, RevokedAt)`.
- [x] **Application ports:**
  - `IRefreshTokenRepository` with `GetByHashAsync`, `AddAsync`, `UpdateAsync`, `RevokeFamilyAsync`, `RevokeAllForUserAsync` and `DeleteExpiredAsync`.
  - `ITokenService` gains `CreateRefreshToken()`, which returns the raw value and its hash, and `HashRefreshToken(string)`.
- [x] **Infrastructure:**
  - `RefreshTokenMap` and `RefreshTokenRepository` on the reflection mapper (T05/T06). No EF, no Dapper.
  - `JwtTokenService` uses `RandomNumberGenerator.GetBytes(32)` (Base64Url) and `SHA256.HashData`.
  - `RefreshTokenOptions` (`RefreshToken` section): `LifetimeDays` from 1 to 30, `ReuseGraceSeconds` from 0 to 120, and `CookieName`. Validated with `ValidateOnStart`, which ties into T11's options validation.
  - Update the `JwtOptions` comment: refresh tokens are no longer out of scope. Set `Jwt:ExpirationMinutes` to 15 in `appsettings.json`.
- [x] **Use cases (`AuthService`):**
  - `LoginAsync` also creates a refresh token (a new family) and returns it **to the API layer only**. The API never writes it into the JSON body.
  - `RefreshAsync(rawToken)`:
    - Unknown, expired or user deleted: `401 auth.refresh_invalid`.
    - Rotated within the grace window: `401 auth.refresh_race`, and nothing is revoked.
    - Rotated outside the grace window: revoke the family, log a warning (user id only, never the token), and return `401 auth.refresh_invalid`.
    - Otherwise: rotate the token and return a new access token, a new refresh token and the user.
  - `LogoutAsync(rawToken?)`: revoke the family. It is idempotent and always succeeds.
  - `UserService.DeleteAsync` also revokes every refresh token of the deleted user.
  - Opportunistic cleanup: on login, delete the user's expired tokens.
- [x] **API (`AuthController`):**
  - `POST login`: same body as today (`AuthResponse`), plus `Set-Cookie: hr_refresh=...`.
  - `POST refresh` (`[AllowAnonymous]`, reads the cookie): 200 + `AuthResponse` and a new cookie, or 401 problem details (and the cookie is deleted unless the code is `auth.refresh_race`).
  - `POST logout` (`[AllowAnonymous]`): revokes the family, deletes the cookie, returns 204.
  - The cookie is written by a small `RefreshTokenCookie` helper in the API layer, because cookies are an HTTP concern. Application never sees `HttpContext`.
- [x] **Docs:**
  - `HeroRegistry.Api.http`: login, then refresh, then logout.
  - README: a "Token lifecycle" section with the table above.
  - OpenAPI: describe the cookie on `refresh` and `logout`.

## Implementation notes
- **Atomic rotation.** `IRefreshTokenRepository.RevokeAsync` updates only while `RevokedAt IS NULL`. Of two requests rotating the same token at the same instant, exactly one wins; the other gets `auth.refresh_race`.
- **Contracts.** `IAuthService.LoginAsync` and `RefreshAsync` return an `AuthSession`: the JSON `AuthResponse`, plus the raw refresh token and its expiry for the cookie. Its `ToString()`, and that of `NewRefreshToken`, mask the raw token.
- **Settings.** `RefreshTokenOptions` lives in Application, because `AuthService` needs the lifetime and the grace window. It is bound and validated at startup in Infrastructure (`RefreshTokenOptionsValidator`).
- **Reuse rules.** A token revoked by logout (no `ReplacedByHash`) is simply invalid; only a *rotated* token presented again triggers the family revocation and the warning (EventId 3001, user id only).
- **Housekeeping.** It uses a physical `DELETE`, timed and logged as the new `DataOperation.Delete`.
- **No caching.** Login and refresh responses carry `Cache-Control: no-store`.
- **Test clock caveats.** API tests use a `FakeTimeProvider`. JwtBearer checks `nbf` against the real clock, so tests do not advance time before using a new access token. `DATETIME2(3)` rounds to the millisecond, so expiry tests step just past the boundary.
